# 发布规则

## 发版本的流程

**发版本时直接提交并打标签，不要修改 `package.json` 里的 `version`。**

```bash
git add <本次改动>
git commit -m "<改动摘要>" -m "<逐条列点>"
git tag v<版本号>
```

- 版本号只体现在标签上，格式 `v<主版本>.<次版本>.<修订号>`，例如 `v2.3.0`
- **提交信息必须写清改动内容**：subject 直接概括本次改动，正文逐条列点
- 按本规则，发版提交不改 `package.json` 的 `version`，所以它**必然包含实际改动**，也就**必然不能**拿版本号当 subject
- 历史里 `2.2.0` 这类只有版本号的提交，其内容确实只有 `package.json` 里版本号的变化（发布流程 `npm version` 的产物），subject 与内容相符，不要照着往功能提交上套
- 判断标准：`git log --oneline`、GitHub 列表、发布页只显示 subject。若光看 subject 不知道这次改了什么，就是不合格的提交信息
- 标签基于 `package.json` 中残留的旧版本号会造成困惑，属正常现象，不要去“修正”它
- 不自动执行 `git push`（含 `--tags`），是否推送由用户决定

## 版本号怎么定

| 变更类型 | 递增位 | 示例 |
|---------|-------|------|
| 新增功能、最低 VSCode 版本提升 | 次版本 | `v2.2.0` → `v2.3.0` |
| 仅缺陷修复 | 修订号 | `v2.2.0` → `v2.2.1` |
| 不兼容的大改动 | 主版本 | `v2.3.0` → `v3.0.0` |
